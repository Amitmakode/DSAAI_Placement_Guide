# OpinionMetrix — Interview Prep

## 1. The Story (Tell it like this in the interview)

"In my last project, the team I supported had a real pain point — customer reviews were piling up in a MySQL database, thousands of them, and nobody had time to go through them manually. Negative feedback about product quality or late deliveries would just sit there until it showed up later as a ratings drop, and by then it was too late to act on it. My job was to turn that pile of raw text into something the support and product teams could actually use in real time.

I started by pulling the data out of MySQL and looking at it properly — and it was messy, like real production data usually is. HTML tags, emojis, duplicate reviews, some completely empty after cleanup. So before touching any model, I spent real time on a proper cleaning pipeline — lowercasing, stripping noise, tokenizing, removing stopwords, lemmatizing — and I made sure it logged what it was doing at each step, because I didn't want silent data loss six months later when someone asks 'why is our data smaller than expected.'

Then came the model decision. I could've gone with a simple TF-IDF plus logistic regression setup — fast, cheap, good enough for a demo. But this was going to be used by actual people making decisions off it, so I fine-tuned a pretrained Transformer instead, DistilBERT to start with, using HuggingFace's Trainer with early stopping so it wouldn't overfit on our relatively small dataset. And here's something I actually had to catch — the reviews were mostly positive, maybe 3-to-1 skewed. If I'd just looked at accuracy I'd have shipped a model that looks great on paper but quietly ignores the negative reviews, which were the whole point of the project. So I tracked weighted F1 and the confusion matrix instead, and used stratified splits so that imbalance didn't leak into evaluation either.

Once I was happy with it, I didn't just hand off a notebook — I built a Streamlit app around it so anyone on the team could paste a review and get a sentiment plus confidence score instantly, no ML background needed. And I closed the loop: every prediction gets written back to the database, so later someone can mark whether it was right or wrong, and that becomes labeled data for retraining down the line instead of the model going stale.

So the way I'd frame the impact: it moved the team from reactively discovering problems in reviews weeks later, to catching them the moment they're written — and it's built so it keeps getting better instead of being a one-time model dump."

## 2. Scenario-Based Interview Q&A (20 Questions)

### Data & Preprocessing

**Q1. A stakeholder says your model is missing obvious sarcasm in reviews. How do you explain this?**
Transformers rely on surface patterns learned from training data; sarcasm needs contextual/world knowledge that's hard to capture without labeled sarcastic examples. I'd suggest adding sarcasm-labeled data, using a larger pretrained model, or accepting it as a known limitation and flagging low-confidence predictions for human review.

**Q2. Your CSV has 20% duplicate reviews. How does your pipeline handle it, and why does it matter?**
`load_data()` drops duplicates on the review text column before training. If left in, duplicates could leak between train/test splits, inflating evaluation metrics and giving a false sense of accuracy.

**Q3. Some reviews are empty after cleaning (e.g., all emojis). What happens, and how would you fix it?**
`preprocess_dataframe()` logs a warning for empty `clean_review` rows. I'd either drop them before training or fall back to raw text/emoji-sentiment mapping so we don't lose signal from emoji-only reviews.

**Q4. Why did you use *light cleaning* for the Transformer but *heavy cleaning* (stopwords, lemmatization) elsewhere?**
Transformers use subword tokenizers and attention over word order/casing/punctuation — stripping that removes useful context. Heavy cleaning is only appropriate for classical models like TF-IDF + Logistic Regression that treat text as a bag of words.

**Q5. The dataset is imbalanced — mostly Positive reviews. How do you handle this?**
I use `stratify` in `train_test_split` to preserve class ratios across splits, and weighted F1/precision/recall in evaluation so the minority class isn't masked by overall accuracy. Class weighting or oversampling (SMOTE, upsampling) could be added if imbalance is severe.

---

### Model & Training

**Q6. Why fine-tune a pretrained Transformer instead of training from scratch?**
Pretrained models already understand general language patterns from massive corpora. Fine-tuning on our (relatively small) review dataset is far cheaper and gives better performance than training a model from random weights.

**Q7. How do you prevent overfitting during fine-tuning?**
I use a validation split with `EarlyStoppingCallback`, `load_best_model_at_end=True` based on F1, weight decay, and warmup — training stops automatically if validation performance stops improving.

**Q8. Your model shows 95% train accuracy but 70% test accuracy. What's your diagnosis and next step?**
That's a classic overfitting signature. I'd check if early stopping actually triggered, reduce epochs/model complexity, add dropout/weight decay, get more training data, or verify there's no train/test leakage from duplicates.

**Q9. Why choose F1 as `metric_for_best_model` instead of accuracy?**
F1 balances precision and recall, which matters more when classes are imbalanced. Accuracy alone can look good while the model still fails on minority classes.

**Q10. How would you choose between DistilBERT, BERT, and RoBERTa for production?**
DistilBERT is faster/lighter — good for real-time inference with limited resources. BERT is a stronger baseline. RoBERTa usually performs best but is heaviest. I'd benchmark all three on validation F1 vs. inference latency and pick based on the app's latency/accuracy trade-off.

**Q11. What does `max_length=128` control, and what happens to longer reviews?**
It's the token limit per input; reviews are truncated (or padded) to this length. Very long reviews lose information beyond 128 tokens — I'd analyze review-length distribution and raise this if truncation is cutting off meaningful content.

### Evaluation

**Q12. Precision for "Negative" reviews is low. What does that mean in business terms, and why does it matter?**
Low precision means many reviews flagged as Negative are actually not — false alarms. If this feeds an alerting system for customer support, it wastes agent time chasing non-issues, so I'd tune the decision threshold or rebalance training data.

**Q13. How do you explain a confusion matrix to a non-technical stakeholder?**
It's a table showing what the model predicted vs. what was actually true for each class — the diagonal is correct predictions, and off-diagonal cells show specific types of mistakes (e.g., Neutral reviews mistaken for Positive), which is more actionable than a single accuracy number.

### Deployment & Engineering

**Q14. Your Streamlit app is slow to start the first time. Why, and how do you fix it?**
`download_models()` pulls model weights from Google Drive on first run, and `@st.cache_resource` ensures this and model loading only happen once per session rather than on every rerun. I'd consider bundling the model with the deployment or using a persistent volume to avoid repeated downloads.

**Q15. How does the app avoid reloading the model on every user interaction?**
Both `download_models()` and `load_predictor()` are wrapped in `@st.cache_resource`, so Streamlit caches them across reruns within the same session/process instead of reloading from disk each time a button is clicked.

**Q16. Where are database credentials stored, and is this secure?**
Credentials come from `st.secrets` (Streamlit secrets management) in the app, and from environment variables via `.env`/`python-dotenv` in the offline script — neither is hardcoded in source, and `.env`/secrets files are excluded via `.gitignore`.

**Q17. What happens if the MySQL database is down when a user submits a prediction?**
`get_connection()` wraps the connection attempt in a try/except that raises after logging an error via `st.error`. Currently a DB outage would break the save step — I'd improve this by making `save_prediction` non-blocking (e.g., log locally and retry) so a DB outage doesn't crash the user-facing prediction.

**Q18. How would you scale this app for 10,000 concurrent users?**
Separate the model-serving layer from the UI — deploy the model behind a dedicated inference API (e.g., FastAPI + batching, or a model-serving tool), horizontally scale that service, and have Streamlit just call the API. Also move to async DB writes/a queue so logging doesn't block predictions.

**Q19. How would you monitor this model in production over time?**
Track prediction distribution drift (e.g., sudden spike in Negative predictions), log confidence scores to catch low-confidence trends, periodically sample and manually label recent predictions to measure real-world accuracy, and set up alerts if metrics degrade — this is where the `correct_sentiment` column in the DB would support feedback-based retraining.

**Q20. A user pastes a review in a different language. What happens, and how would you handle it?**
The tokenizer will still process it, but predictions will be unreliable since the model is trained on English reviews. I'd add a language-detection step (e.g., `langdetect`) before inference and either route to a multilingual model or show a "unsupported language" message.
